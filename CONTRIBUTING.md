# Contributing to Markflow

Thanks for helping. Markflow is for humans and AI agents. You can help with or without AI.

## Start here

Read `README.md` first. Then read `docs/PRINCIPLES.md`. Those two files explain what Markflow is and what it is not.

Pick a small task first. Check open issues. If no issue fits, open one and describe the problem in plain words.

## Two ways to work

### Without AI

Follow the docs in `docs`. Write specs in Markdown. Write code and tests by hand. Run the tests yourself. Open a pull request when it works.

You do not need to install any AI tool. You do not need to set up MCP. Ignore the `.agents` folder if you see one in a user project. It is optional for humans.

### With AI

Let the AI agent read `AGENTS.md` first. It will point to the right docs and specs. Review what it writes. Do not merge code you did not read. Check the tests yourself.

AI help does not remove review. You are still responsible for the change.

## House rules

Use English in all docs and code. Use English in file and folder names too.

Write short sentences. Write like you talk to a teammate. Avoid em dashes. Avoid colons in prose. Avoid formal and cliché words. Avoid words like delve, leverage, seamless, robust, and cutting edge. If a sentence sounds like a sales page, rewrite it.

Keep commits small. One logical change per commit. Use the imperative mood. Keep the subject under 50 characters when you can. Good examples are Add README, Fix typo in PRINCIPLES, and Add project discovery doc. Do not write long commit bodies. A short subject is often enough. If you need more detail, add one or two short lines.

Do not invent architecture or decisions. If you do not know something, mark it as TBD and ask. Do not overwrite files that belong to users without approval. Do not change code outside the scope of your task.

Every doc file should start with a short note on what it is for and when to read it. Keep the README short. Put details in `docs`.

Use kebab-case for file names. Keep file names in English.

## Pull requests

Keep a pull request focused. One idea per pull request is best.

Describe what changed and why in plain words. Say how you tested it. Show the test output or the check you ran when you can.

If the change touches docs, make sure the docs still match the code. If the change touches the CLI later, make sure the help text still matches the real commands.

## Issues

Describe the problem first. Then describe what you expected. Then describe what happened instead. Add steps to reproduce when you can. Keep it short.

## Code of conduct

Be kind. Be direct but respectful. We do not accept harassment or personal attacks. See `CODE_OF_CONDUCT.md` for the full text.
